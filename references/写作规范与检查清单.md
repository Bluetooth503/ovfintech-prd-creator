# 写作规范与检查清单

> 用途：创建/优化模式的质量自检；审查模式的判据与问题分级。
> 依据：需求工程通用标准与实践——ISO/IEC/IEEE 29148（2011 年起取代 IEEE 830 的 SRS 推荐实践）、INCOSE《Guide to Writing Requirements》(2023)、NASA《Systems Engineering Handbook》，以及国内 PRD 写作实践。
> 说明：下表的「六要素」等属本技能的领域约定，用来落实上述标准的通用特性；它不是标准原文的固定结构。

## 1. 单条表述的质量标准

| 属性 | 检查法 | 不合格信号 |
|:--|:--|:--|
| 无歧义 | 能否出现第二种解读？ | 模糊词、代词指代、一句多事 |
| 完整 | 六个要素是否齐（见第 3 节）？ | 缺异常/缺前置/缺后置 |
| 一致 | 与术语表、其他章节是否矛盾？ | 同名不同义、数值冲突、状态不一致 |
| 可验证 | 什么数据/操作能证明它被满足？ | "准确及时""体验友好" |
| 单一 | 是否只装一件事？ | "A 且 B""并""以及"复合句 |
| 可追溯 | 出处、编号是否在？ | 无编号、无来源 |
| 可行 | 技术上、经济上能否实现？ | 要求超出当前技术或预算，且未说明 |
| 必要 | 不做会怎样（业务后果）？ | 说不出业务后果的镀金需求 |

## 2. 模糊表述替换表

| 模糊表述 | 替换方向 |
|:--|:--|
| 快速、及时 | 给量化：P95 ≤ 2s / T+1 内 / 实时（注明频率） |
| 合理、适当、尽量 | 写清判定条件或取值边界 |
| 友好、灵活 | 写清具体交互或可配置项 |
| 较大、较多、大量 | 给数值：≥ X、超过 X 时 |
| 必要时、视情况 | 写清触发条件 |
| 完善、优化体验 | 写清改什么、改成什么 |
| 等等、之类的 | 列全，或写"超出范围的内容以 X 为准" |
| 相应提示、给出提示 | 写提示原话：「……」 |

## 3. 完整性骨架

**功能六要素**（对应模板 2.x.1）：触发入口 / 前置条件 / 操作步骤 / 处理逻辑 / 后置结果 / 异常与提示。

**数据字段**（对应 2.x.3）：字段名 / 类型 / 必输 / 取值枚举 / 校验与提示。枚举列全量取值。

**异常路径必查**（写功能时逐类过）：
1. 校验失败、数据为空；2. 超限（数量、金额、频次）；3. 无权限；4. 重复操作/并发；5. 上游依赖失败（接口超时、渠道不可用）；6. 状态不允许的操作。

**状态**：给全量取值、初始状态、流转条件、终态；状态变更写清由谁/什么动作触发。含状态机时在 1.3 给状态流转图（mermaid `stateDiagram-v2`），状态取值与流转条件须与第 3 章规则一致。

## 4. 写实规则

- 数值：带单位与条件（"单批次 ≤ 500 个待开数据"）。
- 枚举：直接用"∈ {A, B, C}"或逐项列出。
- 文案：提示写原话，加「」。
- 计算口径：有公式照抄公式；没有公式的先与业务确认后补写（确认不了的不写入文档）。
- 引用：规则用 R 编号，功能用 F 编号；跨章节引用写清位置。

## 5. 常见错误清单（审查判据）

| # | 症状 | 检查法 |
|:--|:--|:--|
| 1 | 缺异常与失败路径 | 六要素"异常与提示"是否为空/只有一句"异常时提示" |
| 2 | 模糊表述 | 全文扫第 2 节词表 |
| 3 | 复合需求 | 规则/功能句中出现"且/并/和"且含两个可判定条件 |
| 4 | 混入实现细节 | 出现表名、字段类型、接口协议、框架名 |
| 5 | 缺边界值 | 金额/数量/长度/时间只有方向没有边界 |
| 6 | 缺权限说明 | 操作步骤未写角色；输入输出未见权限约束 |
| 7 | 状态不闭环 | 有状态名但无流转条件/终态 |
| 8 | 提示无原话 | "提示"后无引号内容 |
| 9 | 清单与说明不对应 | 功能清单条目数 ≠ 第 2 章功能小节数 |
| 10 | 术语空转 | 1.2 空白或写"无"（未声明"不涉及"） |
| 11 | 规则不可判定 | 规则文本含第 2 节模糊词或无法用数据验证 |
| 12 | 占位残留 | XXX、填写提示、TBD 未清理 |
| 13 | 篇幅膨胀 | 骨架性文字（不适用声明、重复说明）占比过高；优化模式下总篇幅明显超源文档 1.2 倍（`check_prd.py --baseline` 可判，属体检带而非硬门槛） |
| 14 | 表格缺分隔行 | GFM 表格首行后须有分隔行（由 `-` 和 `:` 组成）；缺则导出 Word 时表格会塌成一行（`check_prd.py` 报中） |
| 15 | AI 腔／模板句式壳 | S3 自由文本扫《表达规范》句式壳（不是A而是B / 真正重要的是 / 先A再B / 值得注意的是…）；表格与规则表不适用 |
| 16 | 流程/数据缺图或缺声明 | 1.3 无业务流程图、1.4 概念模型或数据流图缺失且未写「不涉及」声明（`check_prd.py` FLOW-01 / DATA-01 / DATA-02 报低） |
| 17 | 空壳字段 | 字段标签（现状 / 触发入口 / 异常与提示…）下无实质内容，或只剩整行括号提示（`check_prd.py` HOLLOW-01 报中） |
| 18 | 表格空行未填写 | 表格数据行所有单元格为空（`check_prd.py` TBL-02 报低） |
| 19 | mermaid 图非法 | 图类型不受支持或主干无连接符，渲染失败会让评审看不到流程图（`check_prd.py` MERMAID-01 报低） |
| 20 | 编号不对应 / 悬空引用 | 清单 F 编号与第 2 章小节不一一对应（FUNC-04 报中）；规则引用不存在的 F 编号（RULE-05 报低）；正文引用未定义的 R 编号（RULE-06 报低） |
| 21 | 数据层约束只在功能说明、未进规则表 | 2.x 的「处理逻辑/异常与提示」里出现可判定条件（字段 = 值、>、≤ 等）却未在第 3 章登记为 R 规则；应抽出进规则表，功能说明改为「校验见 Rxx」 |
| 22 | 概念模型该有却没有 | 新增了业务对象、或改变了对象关系（含既有对象新关系），1.4 却声明「不涉及新业务实体」且无理由 |

## 6. 审查报告格式约定

按模板输出问题清单，每条包含：**级别 / 位置 / 问题 / 建议追问**。

- 级别：**高**（影响评审通过或下游理解）、**中**（影响完整性与一致性）、**低**（表达与格式）。
- 报告级别允许按本节示例口径调整脚本判定（如脚本判「低」、示例口径判「高」），并在报告中注明差异；「未执行项」（因章节缺失跳过）随结构补齐一并消解。
- 位置写到章节号与原文片段（引用时原文照抄，限 40 字内）。
- 先列问题，不直接改写文档；用户确认后再进入优化模式。
- 结论分三档：通过 / 修改后通过 / 需补充材料重写。

```markdown
| # | 级别 | 位置 | 问题 | 建议追问 |
|:--|:--|:--|:--|:--|
| 1 | 高 | 3.1.1 异常与提示 | 只写了"给出相应提示"，未给提示原话 | 请提供超限时的完整提示文案 |
| 2 | 中 | R03 | 规则含"金额较大时"，不可判定 | 请给出金额阈值与单位 |
```

## 7. 生成后的自检顺序

1. 运行 `scripts/check_prd.py <文档>`（优化模式加 `--baseline <源文档>` 核对篇幅），按报告逐项处理"高"级问题；
2. **定向抽查、不做全文复读**：抽查第 5 节高风险项（缺异常、模糊表述、复合需求、提示无原话、清单与说明不对应、术语空转、占位残留、篇幅膨胀）——重点看术语表、业务规则表、功能清单与第 2 章对应关系、各节「异常与提示」；
3. 对照模板《提交前自检》逐项勾选；
4. 篇幅核对：优化模式总字数默认在源文档 0.8～1.2 倍（口径与压缩顺序见 `标准需求文档模板.md` §4.8），明显偏离时先按内容完整度判断、再压缩骨架文字（事实与提示原话不动）；
5. 确认未决事项已与用户确认、文档中无未决标记；仍有缺口的，只在交付说明（对话）中列出。
