# 术语与规则写法

> 目的：把术语、业务规则、业务对象与数据流向写清楚——评审读得顺，研发用得上，后续系统解析也顺手。

## 1. 术语（写在 1.2）

**什么该登记**：本需求新出现的业务名词；既有名词但口径有变化；在不同系统/团队间叫法可能不一致的词。

**什么不登记**：纯技术名词（接口、缓存、Token）、页面元素名（按钮、弹窗标题）、无歧义的通用词（时间、数量）。

**定义写三件事**：它是什么 + 从哪来/怎么形成 + 与相近概念怎么区分：

- ✓ 「可用额度：授信额度中尚未占用、当前仍可使用的金额，随放款扣减、随还款恢复。」
- ✗ 「采集价：采集价是采价得到的商品价格」（循环定义）
- ✗ 「质押品种：质押的品种」（等于没写）
- ✗ 「中国工商银行：工行提供的开票渠道」（用自身别称循环定义）

**硬要求**：完整句子；不用术语解释术语；枚举值说清有哪几类（完整取值放业务规则）；**禁止用术语自身的别称解释它**——别称只能进「别称/简称」列。机构/平台类术语的写法：先说它是什么机构/平台，再说本需求中作为什么用（如「电子税务局：税务机关的官方线上开票平台，本需求中指该平台对应的开票渠道」）。

**别称处理**：正文里出现过的口语化叫法，填进「别称/简称」列；正文尽量统一用标准叫法。

**空转处理**：确无新术语时写「本需求不涉及新术语」，不要留空或只写「无」。

## 2. 业务规则（写在第 3 章）

**第一用途**：需求上线后的**数据质量检查**——每条规则最终要能写成一条检查脚本/SQL，在数据里跑出违规记录。评审核对、研发建约束是中间用途，不是终点。因此收录总原则：**落在数据层、违规真实影响业务、宁缺毋滥**。

**收录门槛（四条全过才收）**：

1. **落在数据层**：能写成「字段 X 满足条件 Y」。页面交互约束（按钮禁用、样式、校验时机、弹窗行为、Tab 切换）不进本表，归 2.x.4 交互细节；
2. **违规有业务后果**：影响金额、账务、合规、数据一致性。纯体验、纯便利不收录；
3. **可判定**（见纪律 1）；
4. **宁缺毋滥**：拿不准的一律不收——缺一条规则最多少一条检查，多一条无关规则会污染检查基线。默认不收，需要理由才收。

确无数据层规则时，第 3 章写「本次需求不涉及业务规则」，不要硬凑。

**触发信号**（写作时看到这些才考虑登记）：「不能为空 / 必须存在 / 大于小于 / 只允许这几种取值 / 按公式计算 / 同一 X 只能有一条 / 状态流转与前置状态约束 / 跨字段一致性」。

**六类归属与检查类型**：非空与存在性 / 取值范围 / 条件约束 / 枚举取值 / 计算口径 / 唯一性——每类对应一类数据检查（非空检查、范围检查、枚举检查、唯一性检查、口径重算、条件校验）。

**三条纪律**：

1. **可判定**。「放款日期晚于授信开始日期」可判定；「数据要准确及时」不可判定——写不出判定方法的，与业务确认或拆成可判定的子规则。
2. **一条一事**。含"且/和"的复合约束拆开（"金额 ≥ 0 且 ≤ 授信额度"→ 两条），便于分别校验、分别停用。
3. **过滤分离**。数据范围写进「过滤条件」列，不混进规则正文；空白过滤 = 全量校验（含义明确，无需补写）。过滤条件同时是数据检查的范围限定。

**提示与动作**：写清违规时系统的行为（阻断/报错/默认值/自动计算）与提示原话——这部分供研发与测试消费，不参与数据检查。

**计算口径**：有公式照抄；只有口径没公式的，先与业务确认后补写；确认不了的不写进文档，只在交付说明（未决缺口）里说明。

**与术语联动**：规则引用的字段名 = 1.2 术语表里的标准叫法；规则写不出对应词时，先补术语。

## 3. 业务对象与叫法（全文范围）

**值得成为独立对象的**：有身份的对象（有编号、有状态、可单独查询/建台账，如"结算单""到货单"）；独立存在的事物（资金方、仓库、商品分类）；文档中以表格列出字段的对象。

**不算对象**：字段（"采集价"是采集记录的属性）、动作（"审核""提交"）、页面本身。

**写法要求**：

- 业务对象首次出现用标准叫法，后文保持一致；一个对象不做多种叫法。
- 同一对象的主档、列表、详情页用同一个名字（"客户"就是"客户"，不混用"用户/会员/客户"）。
- 1.4 数据视图的概念模型（mermaid erDiagram）里的实体就是本节认定的业务对象，两者叫法必须一致；实体名用 1.2 标准术语。
- **概念模型条件必填**：有新增或关系变更的业务对象时画在 1.4（关系线写业务动词、基数按业务事实即业务规则、图下配一句「主链 + 分支」，不列属性字段）；确无则写「本次需求不涉及新业务实体」。

## 4. 数据流向（写在 1.4 数据视图）

涉及数据来源或去向变化时必写；固定说清：**来源（系统/角色/线下） / 数据形态变化 / 去向 / 流转类型（同步·推送·补录·卸数·线下） / 是否落库（落哪） / 频率 / 失败处理**。

- 简单场景可一句话：✓ 「过磅数据由地磅系统推送至本系统并落库；开票结果推送至外部开票平台，不落库。」
- 涉及跨系统、落库或线下环节时用结构化小表（列同上述字段），便于后续查漏与提取。
- ✗ 大段叙述系统调用关系（那是技术方案）。

节点叫法与概念模型、1.2 术语一致；只画业务环节间的数据流转，不画接口调用。不涉及数据流向变化时，明确写「本次需求不涉及数据流向变化」。
