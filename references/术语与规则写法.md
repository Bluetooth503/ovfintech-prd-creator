# 术语、规则与数据视图写法

> 用途：把四类产出写稳——**业务术语（1.2）/ 业务规则（第 3 章）/ 概念模型（1.4）/ 数据流图（1.4）**。四者互相引用，叫法必须一致。
> 本文是这四类产出的操作手册（原则 + 步骤 + 自检）；对应的模板骨架与示例见 `标准需求文档模板.md`。

## 0. 四类产出、关系与产出顺序

| 产出 | 位置 | 命名基准 / 依赖 |
|:--|:--|:--|
| 业务术语 | 1.2 术语定义 | 其余三者的命名基准 |
| 概念模型 | 1.4 数据视图 | 实体名 = 术语；关系基数常即业务规则 |
| 数据流图 | 1.4 数据视图 | 节点名 = 术语；对象来自概念模型 |
| 业务规则 | 第 3 章 业务规则 | 字段名 = 术语 |

**按此顺序产出：① 术语 → ② 概念模型 → ③ 数据流图 → ④ 业务规则。**
理由：后三者都要用术语的标准叫法，所以术语先定；概念模型定下的对象与基数，会成为数据流图的节点与业务规则的来源；规则最后写，字段名回指术语。

## 1. 提取业务术语（写入 1.2）

**何时做**：材料里出现 ① 本需求新业务名词、② 口径有变化的既有名词、③ 跨系统/团队易混的叫法。**不收**：纯技术名词（接口、缓存、Token）、页面元素名（按钮、弹窗标题）、无歧义通用词（时间、数量）。

**原则**：

1. **一个概念一个标准叫法**：全文（含功能清单、业务规则、两张图的节点）统一；别称只能进「别称/简称」列。
2. **定义写三件事**：它是什么 + 从哪来/怎么形成 + 与相近概念怎么区分；完整句子，不用术语解释术语。
3. **禁止循环定义**：不得用术语自身的别称解释它本身。
4. **只写业务语言**，不含技术实现。
5. **可声明不涉及**：确无新术语写「本需求不涉及新术语」，不留空、不写「无」。

**步骤**：

1. **划名词**：通读材料，圈出全部业务名词（实体、单据、状态、角色、指标）。
2. **并叫法**：同一事物的不同叫法合并为一条，非标准叫法移入「别称/简称」列。
3. **定取舍**：逐个按"何时做"判定是否收录；拿不准的先与用户确认，不自行取舍。
4. **写定义**：按三件事写成完整句；枚举型术语写清有哪几类（完整取值放第 3 章）。
5. **回指统一**：把全文与两张图的叫法改到术语表的标准叫法。

**自检**：定义是完整句、无循环、无技术词；全文同一叫法；概念模型实体名、数据流图节点名都能在术语表找到。

**示例**：✓ 「可用额度：授信额度中尚未占用、当前仍可使用的金额，随放款扣减、随还款恢复。」 ✗ 「质押品种：质押的品种」（等于没写）；✗ 「中国工商银行：工行提供的开票渠道」（用自身别称循环定义）。

## 2. 提取业务规则（写入 第 3 章）

**何时做**：凡是能写成「字段 X 满足条件 Y」的**数据层可判定约束，一律登记到本表**——即使它先出现在 2.x 功能说明或「异常与提示」里，也要抽出来进规则表，不能只留在功能描述（例：「开票状态 = 待开票」「开票金额 > 0」这类可校验条件）。只有**页面交互约束**（按钮禁用、样式、校验时机、弹窗行为、Tab 切换）才归 2.x.4 交互细节。

**第一用途**：需求上线后的**数据质量检查**——每条规则最终要能写成一条检查脚本/SQL，在数据里跑出违规记录。评审核对、研发建约束是中间用途。

**原则（四条门槛，全过才收）**：

1. **落在数据层**：能写成「字段 X 满足条件 Y」。
2. **违规有业务后果**：影响金额、账务、合规、数据一致性；纯体验、纯便利不收录。
3. **可判定**：写得出"什么数据能证明它违规"。
4. **宁缺毋滥**：拿不准的一律不收——缺一条规则最多少一条检查，多一条无关规则会污染检查基线。

**纪律**：一条一事（含「且/和」的复合约束拆开）；过滤条件分离（数据范围进「过滤条件」列，空白 = 全量校验）；提示给触发动作 + 原话；**数据层约束不留在功能说明**——可判定条件一律进规则表，功能说明里只用「校验见 Rxx」引用。

**步骤**：

1. **扫信号**：找「不能为空 / 必须存在 / 大于小于 / 只允许这几种取值 / 按公式计算 / 同一 X 只能有一条 / 状态流转与前置状态约束 / 跨字段一致性」。
2. **过门槛**：逐条判四条门槛，不合格的不收。
3. **拆条**：出现「且/和」的复合约束拆成一条一事，便于分别校验、分别停用。
4. **分离**：数据范围搬进「过滤条件」列。
5. **补动作**：写清阻断 / 报错 / 默认值 / 自动计算 + 提示**原话**（材料有原话照抄；没有的不编造，列入未决缺口）。
6. **归类编号**：按六类归位（非空与存在性 / 取值范围 / 条件约束 / 枚举取值 / 计算口径 / 唯一性），编 R01、R02…

**自检**：条条可判定、一条一事、过滤条件分离、有触发动作与提示原话；每条字段名都能在 1.2 找到；确无数据层规则时写「本次需求不涉及业务规则」。

**联动**：规则引用的字段名在 1.2 找不到的，先补术语再写规则。

## 3. 画概念模型（写入 1.4 数据视图）

**何时做**：只要本需求**新增业务对象、或改变对象之间的关系**（包括既有对象之间出现新的业务关系，如"按渠道拆单"改变了待开票数据与发票的对应关系），就必画。仅当整篇需求既不新增对象、也不改变任何对象关系（纯字段/文案/界面调整）时，才写「本次需求不涉及新业务实体」，并给一句理由。

**原则**：

1. **只画对象与关系**：不画属性、字段、表名、外键——那是逻辑/物理模型，属技术方案。
2. **实体名 = 1.2 术语**，一个对象一个名字。
3. **关系写业务动词**（推送形成 / 开票生成 / 金额回填 / 收款后创建），不写「关联」「有关」这类空动词。
4. **基数按业务事实（即业务规则）判断**：一笔 X 对应几笔 Y；可选/必选按业务事实。
5. **一张图 + 一句「主链 + 分支」**：只写流转主干，不列属性、枚举、字段清单。
6. **简洁**：只收关键业务对象，不堆砌。
7. **"关系变"也算**：不只看"有没有新对象"——既有对象之间出现新关系或关系基数变化，同样要画出来。

**步骤**：

1. **列对象**：从材料与术语表挑出业务对象——有身份、可单独建台账/查询的事物（结算单、发票、客户…）。字段、动作、页面本身不算对象。
2. **连关系**：两两判断是否有业务动作连接，用业务动词命名。
3. **定基数**：标 1:1 / 1:N / M:N 与可选性；能转成可判定约束的，登记为业务规则。
4. **定主链 / 分支**：哪几个对象是主线，主线外有哪些支线。
5. **画图**：mermaid `erDiagram`，实体名与关系动词对齐术语。
6. **复核**：实体名 = 术语；基数与第 3 章规则一致。

**自检**：无属性/字段/表名；实体名在术语表；关系是业务动词；基数与规则一致；图下配了「主链 + 分支」。

## 4. 画数据流图（写入 1.4 数据视图）

**何时做**：只要本需求涉及数据在**角色 / 外部系统 / 数据存储之间流转**（首次出现或改变流向、落库、跨系统提交、结果回填等），就必画。仅当整篇需求完全不涉及数据流转（如纯展示、纯字段/文案调整）时，才写「本次需求不涉及数据流图」，并**用一句话说明理由**（例："仅界面文案调整，数据不动"）。用 mermaid `flowchart` 画**业务层**数据流图，节点与连线只出现业务语言。

**四类元素（形状固定，评审一眼可分）**：

| 元素 | 含义 | mermaid 形状 |
|:--|:--|:--|
| 外部实体 | 数据的源/汇：角色、外部系统、线下环节 | 方框 `A[财务角色]` |
| 加工 | 对数据做转换的业务环节（动词短语） | 圆角 `B(提交开票)` |
| 数据存储 | 数据落库处（业务台账/对象，不写表名） | 圆柱 `C[(待开票数据)]` |
| 数据流 | 数据流动的路径，边上标注所流的数据 | 箭头连线，如 `A --> B` 边标「待开票数据」 |

**原则**：

1. **只画业务层**：节点名 = 1.2 术语，与概念模型叫法一致；不写接口、表名、网段。
2. **数据流合法**：数据流在加工之间流动，或 外部实体 → 加工、加工 → 数据存储；外部实体不直连数据存储，数据存储不连数据存储。
3. **进出守恒**：每个加工至少一进一出；无只有输入或只有输出的孤立节点。
4. **一张主干图**：默认画端到端主干（数据从哪来 → 经哪些环节 → 到哪去）；环节多时按加工拆子图，单图加工 5–9 个。
5. **标注到位**：每条流写清所流的数据；是否落库、跨系统交接点在图里体现；频率、失败处理等图说不清的，写进图下说明。
6. **复用既有通道 ≠ 不涉及**：只要数据在角色/系统/存储之间有路径，就画出来——"复用现有系统/接口"不是不出图的理由。

**步骤**：① 定边界，圈出外部实体（角色/外部系统/线下）；② 列加工与数据存储（业务环节 + 业务台账）；③ 连数据流并逐条标注所流数据；④ 用 mermaid 画主干，复杂处按加工拆子图；⑤ 校验合法性与命名一致，无变化则声明不涉及。

**自检**：四类元素齐全；数据流始于加工、止于加工（或起于外部实体、止于数据存储）；无孤立节点；节点名与概念模型、1.2 术语一致。

**示例**：✓ 端到端主干清楚：财务角色 → 提交开票 →（待开票数据落库）→ 开票中台 → 金额回填结算单。✗ 大段叙述系统调用关系，或写出接口名、表名（那是技术方案）。

## 5. 生成后的总自检（四类产出一起过一遍）

- [ ] 新出现的业务名词都进了 1.2；定义是完整句子；无空转；
- [ ] 全文业务对象叫法统一（含功能清单、规则、输入输出、图节点与占位标注）；
- [ ] 概念模型：无属性/字段/表名，实体名 = 术语，关系 = 业务动词，基数与规则一致，图下有「主链 + 分支」；若新增对象或改变了对象关系，已给出 erDiagram；
- [ ] 数据流图：四类元素齐全、数据流始于加工/止于加工、无孤立节点、节点名 = 术语；若声明不涉及，已确认"数据确实不流转"并给了理由；
- [ ] 业务规则条条过四条门槛、一条一事、过滤条件分离、有提示与动作；数据层可判定约束都已进规则表（未只留在功能说明）；
- [ ] 规则字段名都能在 1.2 找到对应术语（找不到的先补术语）；
- [ ] 别称已集中；正文与别称列不冲突。
